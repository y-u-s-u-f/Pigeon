# Pigeon

A macOS email and calendar client in Rust + GPUI (`gpui-kit` 0.8, imported as `gpui`, with gpui-component). Native rendering, no webviews. Local-first: a SQLite cache, an outbox for writes, and polling against Gmail, Calendar and People; there is no server. Linked to Google since backend sprint 1, and `PIGEON_DEMO=1` runs on generated demo data.

Where to look: `docs/ARCHITECTURE.md` (layers, module index, "where do I add X"), `docs/UI.md` (tokens, colors, motion, shared controls), `docs/GLOSSARY.md` (vocabulary), `docs/adr/` (why the big choices were made), `docs/ROADMAP.md` (every feature and its status).

## Current state

- Linked to Google and usable as a daily driver on one account. What is left is in `docs/ROADMAP.md` §2: checks only the user can do, an account with a second verified address, and the items still ⚪.
- `main` ships; work lands by PR. The app is installed with `scripts/install.sh` after a merge, only when the user asks or a sprint says so.
- The sprint docs (`docs/*_SPRINT.md`) record how earlier sprints ran. They are history, not rules; the rules are here and in the `sprint` skill.

## Principles

- Blazing fast and lightweight. No webviews, no heavy dependencies.
- Keyboard-centric: every action has a shortcut and shows up in ⌘K. Actions, keymap and the command table live in `src/actions.rs`.
- Minimal and flat (Linear, Superhuman). The whole window is translucent glass. Light and dark follow the system.
- YAGNI. Prefer boring, known solutions. Match the surrounding code; keep comments sparse.

## Polish bar

Every change is held to this, not just polish sprints.

- **Apple Human Interface Guidelines.** Follow the macOS and general HIG: native behavior for menus, shortcuts, focus, selection, scrolling, window chrome, accessibility (VoiceOver, Reduce Motion, Increase Contrast, text size), and wording. When a custom control would behave differently from the macOS one, match macOS unless there's a clear reason not to.
- **Don't do too much.** Before writing something, check whether Rust's std, GPUI, gpui-component or an existing helper in this repo already does it. No hand-rolled versions of what exists, no needless abstraction, no slower option when a faster one is just as simple. Simplifying code must not change how the app looks or behaves.
- **Motion with intent.** Animate what helps people follow a change (things appearing, leaving, moving, resizing, state toggles); don't animate what should feel instant (typing, selection, hover color, keyboard navigation through lists). Use the springs and helpers in `src/ui/motion.rs`, never linear or ad-hoc durations: arrivals springy and quick, exits shorter with no overshoot, everything interruptible and retargetable, and Reduce Motion respected. If no token fits, add one there.
- **Finish it.** Hover, pressed, focused, disabled, empty, loading and error states all handled; alignment, spacing and text sizes consistent with the surrounding UI. It should feel built with care, not just work.

## Code conventions

- Colors only from `src/theme.rs`. Text sizes, spacing, radii, hit targets and focus helpers from `src/ui/style.rs`, motion from `src/ui/motion.rs`, shared controls from `src/ui/controls.rs` and `src/ui/mod.rs`; no raw px for these. `docs/UI.md` lists every token and when to use it.
- Give interactive elements `.role(..)` and `.aria_label(..)`.
- Don't edit `assets/*.json` unless asked. Demo data is generated by a Claude Haiku 5.5 agent (`anthropic/claude-haiku-5-5`).
- UI wording follows `docs/GLOSSARY.md`: "conversation", "demo data", "All Mail"; US spelling ("color", "canceled", "labeled"). Title case for buttons, menus, commands and segments; sentence case for tooltips, settings rows, descriptions and toasts.
- A new action needs its entry, keymap and ⌘K command in `src/actions.rs`; one without the others is half a feature.

## Tests

- Unit tests sit next to the code in `#[cfg(test)]` modules. Add one when a bug or a rule can be expressed without the GUI.
- Implementers run `cargo fmt` and `cargo clippy --all-targets` (no new warnings), not `cargo build` or `cargo test`; the main agent runs those before committing and sends failures back to be fixed.
- Never test the GUI with a subagent or a second harness. The main agent does it in Codex, at the end of a sprint or when the user asks.

## Workflow

For a sprint, a push across several workstreams, load the `sprint` skill first (`.opencode/skills/sprint/SKILL.md`) and follow it; it writes the plan in `docs/` and runs this workflow.

1. One or more `implementer` agents make the changes. If there's a lot, split by non-overlapping files.
2. The main agent tests the GUI in Codex: it runs `codex exec -m gpt-6.1-terra` in a background shell, with Codex's built-in computer use and its `cua_repl` tool (no subagents, no third-party `cua-driver`; say so explicitly, since Codex can confuse the two).
3. A fresh `implementer` fixes what Codex reports. Re-test the failed items.
4. The main agent commits and opens the PR (`file-pr` skill).
5. Review with the `code-review` skill, against the PR's base branch. The spec is the user's original request plus the feature's entry in `docs/ROADMAP.md`; never the sprint docs or `UX_REVIEW.md` unless the user points to them. Fresh `implementer` agents fix the findings (not `general`), split by non-overlapping files. Fixes are not GUI re-tested.
6. The main agent runs `cargo build` and `cargo test`, commits the fixes and pushes to the PR branch.
7. After the merge, when the user asks or the sprint says so, the main agent runs `scripts/install.sh` and reports the installed commit (`git rev-parse --short HEAD`).

Don't have one agent implement, test and fix in a loop. Subagents don't commit; the main agent does.

## Standing preferences

- **Models.** `implementer` is `claude-agent/opus`; GUI testing is `codex exec -m gpt-6.1-terra`. Use the model or agent the user names and say so before swapping.
- **Testing cadence.** Tests, fmt and clippy on every change; GUI checks at sprint end or when asked, not after every edit.
- **Autonomy.** In an unattended run, pick the best option, write it down and keep going; don't stall on a question you can answer yourself.
- **Secrets.** Never print or commit them, and never read `.env`. Key names only.

## Roadmap

`docs/ROADMAP.md` must always be current. Every change that adds, changes or removes a feature updates it in the same commit: the item's entry and status (⚪ Not done / 🟡 Partially done / 🟢 Fully linked), the section and overall counts, and new items for new features or plans the user mentions. A new or touched entry follows the entry format in the roadmap (What, Done when, Needs, Files) and sets its Verified cell when a check has actually run. Implementers update it with their change; the main agent checks it before committing.

## Running and testing

- Run with `scripts/run.sh` (release build, signed with the local `Pigeon Dev` identity so the Keychain keeps trusting it across rebuilds; plain `cargo run --release` works but the Keychain asks again after every build). `PIGEON_DEMO=1` runs on demo data. Agents running in parallel use their own `CARGO_TARGET_DIR` in `/private/var/folders/sc/26v_9jsx0s9_fkjttv6jzjdh0000gn/T/opencode`; the main agent deletes it when the agent finishes.
- Environment: `PIGEON_DATA_DIR` moves the data folder (and `pigeon.log` inside it), `PIGEON_DEV=1` with `PIGEON_SAVE_DIR` sends saves straight to a folder, `PIGEON_PROFILE=1` runs the profiling mode, `PIGEON_AI_*` and `PIGEON_JEV_*` point the AI service at a model. The full list is in `src/logging.rs`, `src/settings.rs` and `src/backend/mod.rs`.
- GUI testing uses Codex's built-in computer use, scoped to Pigeon's pid and window. Launch the test copy with `open -n -a <Pigeon.app> --env PIGEON_DATA_DIR=… --env …` (a `&` child dies with Codex's shell, and computer use would launch Pigeon without the environment), then check it with `ps eww -p <pid>`. Never send input to other apps. Never change system appearance or wallpaper; test dark mode in a scratch copy. Real-account safety rules are in `docs/BACKEND_SPRINT_2.md` §4 and still apply.
